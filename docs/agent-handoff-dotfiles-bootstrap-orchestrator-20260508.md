# Agent Handoff: bootstrap orchestrator (single entry point)

## status
open

## type
design-consult

## owner
Human

## next_owner
Human

## priority
high — Without a single entry point, every other dotfiles strengthening track has to bolt itself onto an ad-hoc set of scripts, and the user's stated requirement ("simple means like running a batch") cannot be satisfied.

## goal
Define one canonical bootstrap command that takes a fresh Linux/macOS box from "git cloned dotfiles" to "fully usable daily environment", orchestrating every other phase (system packages → dotfile symlinks → editors → language toolchains → Claude/Codex assets → secrets → verification).

## context
- The user wants the dotfiles repo to be the base for the entire personal environment and to be redeployable with "one batch run" on a new Linux or macOS host.
- Today the bootstrap flow is split across at least three scripts and several manual `SETUP.md` steps:
  - [setup.sh](../setup.sh) — symlinks dotfiles, calls `bin/sync-codex-skills.sh`.
  - [setup-claude.sh](../setup-claude.sh) — Claude Code assets only, generates `~/.claude/settings.json` from template.
  - [bin/sync-codex-skills.sh](../bin/sync-codex-skills.sh) — Codex skill symlinks.
  - Manual: Neovim install, Flutter/JDK/Android, Node.js, rbenv, starship, system packages, secrets, MCP env file.
- The two scripts assume Linux paths and bash; macOS portability is unverified.
- There is no explicit dependency order, no dry-run mode, no rollback, no progress reporting.
- This handoff is the umbrella for the rest of the dotfiles strengthening tracks; it does not implement them, only chooses how they are wired together.

## current state
- [setup.sh](../setup.sh) creates dotfile symlinks and bootstraps `~/bin/`, `~/.config/nvim`, `~/.config/starship.toml`, `~/.codex/skills/`. No system-package installation, no toolchain installation.
- [setup-claude.sh](../setup-claude.sh) is independent of `setup.sh` and must be run manually as a second step. It silently emits warnings (not errors) when `claude/.mcp.env` is missing.
- [SETUP.md](../SETUP.md) lists ~6 manual steps after `setup.sh` (Neovim, plugins, shell restart, Claude install, Claude setup, Codex install) — none of which are scripted.
- [docs/requirements.md](requirements.md) labels Mac support as wishlist; nothing else captures the macOS branch.

## options
| option | summary | tradeoff | recommendation |
|---|---|---|---|
| A. Single `bootstrap.sh` orchestrator | One top-level script invokes every phase in order with `--phase` selection and `--dry-run`. | Concentrates complexity but forces every phase to expose a clear contract. | ✓ |
| B. Make-based driver (`make bootstrap`, `make claude`, `make verify`) | Depends-on graph for free, parallelizable, idempotency tracking via timestamps. | Adds Make as a hard prerequisite; less ergonomic on stripped-down macOS systems. | |
| C. Keep scripts split, add a top-level README playbook | Minimal change, just document the order. | Does not satisfy the "one batch" requirement; relies on the user to remember sequence. | reject |

## recommendation
Adopt option A: a top-level [bootstrap.sh](../bootstrap.sh) (to be created) that detects OS/arch, then runs phases in this order — system packages → dotfile symlinks → toolchains → Neovim → Claude assets (including the memory/state sync step, see claude-state-sync handoff) → Codex assets → MCP env → verification. Each phase delegates to a script under `lib/bootstrap/<phase>.sh` (new directory) so individual phases stay testable and re-runnable. OS/arch detection lives in one shared helper, `lib/bootstrap/os-detect.sh`, sourced by every phase script — phase scripts must not call `uname` directly, so detection logic (including WSL2) changes in exactly one place. Existing `setup.sh` / `setup-claude.sh` become thin shims that call into the new structure to preserve muscle memory.

## acceptance criteria
- [ ] `bash bootstrap.sh` on a freshly cloned dotfiles repo brings the host to a usable state without further manual steps (secrets being the explicit exception, see secret-management handoff).
- [ ] `bash bootstrap.sh --dry-run` prints the actions it would take without modifying the host.
- [ ] `bash bootstrap.sh --phase claude` runs only the Claude phase.
- [ ] Re-running `bootstrap.sh` is idempotent: no destructive overwrite of state generated by earlier runs.
- [ ] `setup.sh` and `setup-claude.sh` continue to work for backward compatibility (warn-and-delegate).
