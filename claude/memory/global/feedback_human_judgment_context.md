人間が「これでいい / NG / 一部修正」を判断できるだけの情報を提示してから問う。Track A / Slice 2 / AC3 のような handoff 内部用語のラベル列挙では判断不能。

**Why:**
- 2026-05-08 / ai-agent-workflow リポジトリの HO-W026（強化方針推奨）で、Track A/B/C のラベルだけ並べた完了報告を出して指摘を受けた。「全体的に、人間に対して判断を迫る場合に、前提の説明が十分ではないと感じます。人間の判断が可能なようにきちんと必要な情報を文章で提示してください」
- handoff を read していない人にとって、内部 ID と推奨内容は別物。圧縮しすぎたサマリーは判断材料にならない
- 「次タスク提案には画面とユーザー効果を併記」（feedback_next_task_proposal_context.md）の上位概念として、Human escalation 全般に適用する

**How to apply:**
- Human escalation の Stop Report、判断確認、推奨の提示、選択肢提示の場面では以下を文章で含める:
  1. **背景**: このタスク・handoff が何を扱っているか（リポジトリ性質、上流 handoff、起点）
  2. **前提**: 判断の制約（採用者数、ルール導入時期、依存関係、決定基準ドキュメント）
  3. **観測した事実**: 重要度付きで 4〜6 件以内
  4. **選択肢**: 各選択肢に 1〜2 行の根拠（なぜ採用 / 却下 / 保留）
  5. **具体的な変更案**: First Slice なら現状文 → 変更後文を diff で示す
  6. **影響範囲・リスク**: ファイル数、commit 数、参照壊れの可能性、緩和策
  7. **Codex やサブエージェントに渡しているなら何を見てもらっているか**
  8. **判断ポイント**: 何を選べばよいか、選択肢を表で
- 内部用語（Track / Slice / AC# / P6 / handoff_status）を使うなら **必ず日本語の意味を併記**（例: 「Track A（README.md のステータス欄を rolling 表現に書き換える）」）
- handoff/IDEA への back-reference リンクだけで済ませない。本文で要点を再述する
- 反対に、handoff 内部の自動採用 / Codex review 等で人間判断を介さない経路では、ラベルでの圧縮表現で良い（Stop Report と Auto-adoption Log は別物）
- セッション開始時の Q1〜Q3 自動解決の通知でも、Target が何を達成するか・どこを触るかを 1 行で添える
