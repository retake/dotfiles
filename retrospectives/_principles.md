# 運用原則（抽象化済み）

複数の具体教訓から抽象化した運用原則。個別の episodic（具体事例）は各振り返りファイルを参照。
新しい retrospective を追加した際は「既存原則の派生元に該当するか／新クラスタか」を判定し、該当すれば派生元に追記、3件以上の新しい同型が溜まれば新原則として追加する。

## P1: テストハーネスは「副作用・時間・位置」を封じる設計にする

テストで不安定化する主因は、副作用（外部コマンド・連続非同期・SnackBar キュー）・時間（Timer.periodic の実時間）・位置（find.byType の N 番目）を封じていないこと。
実装と同時にハーネス側で以下を用意する：

- **副作用**: stdin・外部プロセス依存はテスト側で `< /dev/null` 等で封じる。非同期ループ発火時は `pumpAndSettle` ではなく `pump()` + `pump(Duration)` で必要最小限だけ進める
- **時間**: Timer.periodic は `CountdownTimer` 相当の抽象を噛ませて tick を手動注入できる形にする
- **位置**: Widget finder は `find.byType(X).first` ではなく `find.widgetWithText(X, 'label')` でラベルで一意特定する
- **再現性**: バグ修正テストは「修正を一時巻き戻して赤転するか」で本症状の再現を確認する。緑のみは機能保証テストに留まる

改修規模の見積もりは行数ではなく「既存の純関数化・Fake 注入点・抽象インタフェースの有無」で決まる。ハーネスが揃っていれば大改修でも TDD で短時間に収束する。

**派生元**: 2026-04-claude-set.md, 2026-04-alarm.md, 2026-04-alarm-7.md, 2026-04-alarm-20.md, 2026-04-alarm-21.md, 2026-04-alarm-23.md, 2026-04-alarm-29c.md, 2026-05-alarm.md（_FixedClock atDeparture は出発時刻ジャストではなく -10s 設定）, 2026-05-alarm-2.md（widget test の tick emit は pumpWidget 後）

## P2: 環境・プラットフォーム前提は着手前に確認する

事後の linker error / 無音 / 例外は手戻りが大きい。ライブラリ追加・ツール選定・実機体験の前に以下を確認する：

- **アーキテクチャ**: ネイティブ依存ライブラリの bundled binary arch・compile-time マクロ・対象 OS を確認する
- **ツール存在**: 技術スタック確定時に依存ツール（pytest・flake8 等）の存在確認とインストールまで行う
- **プラットフォーム分岐**: プラットフォーム依存パッケージ（wakelock_plus 等）は `kIsWeb` / `Platform` チェックで未対応環境を明示的に弾く。パッケージ側の例外に依存しない
- **実機検証の早期化**: 音声・グラフィックスなど環境依存度の高い体験は、選択肢の比較表を出す段階でアクションに「実機検証」を含める
- **管理外ツリーの扱い**: pub-cache / node_modules の直接編集は一時手段に限定し、永続化策（fork / postinstall / override）を決めてから依存する
- **dotfiles リンク**: シンボリンクはディレクトリ丸ごとではなく個別ファイルで張る
- **cron の実行環境は対話シェルと違う**: PATH にシステム版の古いツールしか無いことがある。node/npx のような多重インストールされるツールは絶対パスで解決する（npx のパスだけ差し替えても shebang の `env node` が PATH 先頭を掴む）
- **worktree は生成物を引き継がない**: node_modules・型定義（`wrangler types` 等）は git 管理外なので、worktree を切ったら root とサブプロジェクトの**両方**で install と生成物コマンドを回す。片方漏れは後続エージェントが環境要因で ESCALATED し、原因切り分けに時間を使う
- **セットアップ系 CLI は設定ファイルを書き換える**: `wrangler d1 create` のように、リソース作成コマンドが設定ファイルへ binding を追記することがある。複数環境の設定が 1 ファイルに同居する構造では、追記が環境の分離を壊す（prod の設定に staging の binding が入る等）。実行後は必ず diff を読む

環境カタログ（`~/dev/environments/_index.md`）を着手前に参照する。

## P3: サブエージェント運用は「境界・カウント基準・独立検証」で安定化する

サブエージェントは便利だが、委譲境界と停止条件を事前に決めないと迷走する。以下を徹底する：

- **allow リスト**: 自動実行させるコマンドは委譲前に settings.json の allow に追加する
- **呼び出し方法**: カスタムエージェント（`~/.claude/agents/`）は Agent tool の subagent_type ではなく `@agent名` で呼び出す
- **委譲の粒度**: 大規模コメント削除・import 整序のような機能に影響しない変更は、Reviewer に委ねず設計承認時に Implementer へ一括実施させる
- **レビューループのカウント基準**: 「ロジック不具合の修正のみ」を1周とカウントする。コメント削除・import 整序等は自動修正としてカウントしない。構造的欠損（分岐がない）があると5回でも足りない → 初稿で潰す
- **停止条件**: Tester が同一テストで3回連続失敗したら自律修正を続けず、手動検証移管か設計再考に切り替える
- **独立検証**: サブエージェントの「既存バグ / HEAD で再現」判定は、Orchestrator 側で `git stash` + 該当テスト単独実行で独立検証してから信じる
- **実行コマンドは正規経路と一致させる**: allow リストに合わないからと代替コマンドを指示すると、正規経路では起きない障害を作り込む（例: `cd sub && npm test` の代わりに root から `--config` 指定させ、多重バージョン解決でテストランナーが壊れた）。合わないなら agent 定義の tools を直すか、Orchestrator が代行実行する
- **タイムアウトは「何も起きなかった」ではない**: 実装ターンが時間切れで打ち切られても、作業ツリーには完了間際の成果が残っていることがある。ログが空でも作業ツリーを確認してから次の手を決める。気づかず再実行すると二重作業になり、自動ロールバックさせると完成物を捨てる

**派生元**: 2026-04-claude-set.md, 2026-04-alarm.md, 2026-04-alarm-2.md, 2026-04-alarm-14.md, 2026-04-alarm-20.md, 2026-04-alarm-23.md, 2026-04-alarm-29c.md, 2026-08-logsite-2.md

## P4: ドキュメント同期は即時化し、用語は第一定義に寄せる

ドキュメントの遅延同期は traceability を崩す。以下の運用で乖離を防ぐ：

- **実装直後更新**: 手動実装でも実装直後に design-summary.md・traceability.md を更新する。orchestrate 非経由の修正でも同じリズムを適用する
- **2段運用**: `/audit-handoffs` → `/archive-handoffs` で残課題の視認性を維持する。採用完了したハンドオフは即 archive して /audit 対象から外す
- **用語の正規元**: 用語揺れは「名前の根拠がある方（enum / class 名などの第一定義）」を正とし、派生・コメント・テスト文言を寄せる。リネーム系リファクタは新規テスト不要、既存テストの緑維持が回帰条件

**派生元**: 2026-04-alarm.md, 2026-04-alarm-2.md, 2026-04-alarm-3.md, 2026-04-alarm-10.md, 2026-04-alarm-12.md, 2026-04-alarm-14.md, 2026-04-alarm-21.md, 2026-04-alarm-29c.md, 2026-04-alarm-30.md

## P5: ユーザー報告は字面で受け取らず、切り分けと実ログで検証する

即「コード修正」に走ると誤った方向に時間を使う。以下の順で確認する：

1. **切り分け**: 現象が「コードの問題」「環境の問題」「ライブラリの問題」のどれかを最初に特定する
2. **実ログ優先**: 字面の症状ではなく、実ログ・スタックトレースを最優先で確認する
3. **再現性**: 再現手順を得てから修正に入る

## P6: Flutter/Riverpod の dispose・非同期は「参照の事前捕捉」で組む

dispose 後の ref アクセス・SnackBar キュー・一時的な状態変更の三領域で事故が起きやすい。パターンで固定化する：

- **dispose で ref を使わない**: `ConsumerStatefulWidget` の dispose では ref が無効。外部サービスへのクリーンアップは initState で参照をキャッシュ（`_service = ref.read(serviceProvider)`）して dispose で呼ぶ
- **delayed callback の参照捕捉**: SnackBar 等の delayed callback で WidgetRef を使わず、Notifier 参照をクロージャに事前捕捉する
- **SnackBar キュー**: ウィジェットテストの SnackBar 検証では、他所から出る先行 SnackBar がキューを占有していないか確認する
- **一時オーバーライドパターン**: 永続データを汚さず進行中セッションでのみ変更を効かせたい場合、state に `overrideX: T?` を追加し `effectiveX` getter で合成して露出する
- **破壊的 UI 操作**: style 不変の `onPressed` async 化 + AlertDialog による二重確認で、既存 WCAG テストを維持したまま誤タップ耐性を確保する

**派生元**: 2026-04-alarm.md, 2026-04-alarm-3.md, 2026-04-alarm-5.md, 2026-04-alarm-7.md

## P7: 設計レビュー前に「例外系・既存テスト影響・レイアウト予算」を詰める

初稿が正常系だけだとレビュー周回が嵩む。レビュー前に以下を自己チェックする：

- **例外系の4問**: 「ファイル不在は？」「ESCALATED は？」「カウントは before/after？」「DONE は1通りか？」で例外フローを埋める
- **既存テスト影響の洗い出し**: UI 構造変更（ExpansionTile 折りたたみ等）で壊れる既存ウィジェットテストを Implementer に渡す前に特定する
- **レイアウト予算**: 縦スペースが増える変更では「viewport 高さ予算（例: 800×600 で残り 544px）」を明示して階層レイアウトを比較する

## P8: golden テストの運用は「更新単位・撮影スコープ・許容可否」を事前に決める

視覚回帰テストは「撮りっぱなし・まとめ更新・差分許容を都度判断」で崩れる。golden 追加時・更新時に以下を事前に決める：

- **更新単位**: 複数 REQ で重複更新される場合は REQ 単位で都度再生成してコミットに含める。最後にまとめて焼くと diff 追跡が困難になる
- **撮影スコープ**: widget 単体 golden は要素の正しさを見るが、実 UI（背景色・レイアウト相互作用）との乖離は捕捉できない。主要画面は AppScreen 撮影（画面丸ごと）に上げてスクリーン全体を検証する
- **許容可否**: 差分の意図通り/意図外判定は tester プロンプトで事前に「どの stage/widget で差分が出るのが意図通りか」をリスト化する。`--update-goldens` の判断を tester に丸投げすると意図外の差分を許容してしまう
- **追加の選定**: 新規 golden 追加の優先順位は「コード行数が大きい／状態分岐が多い／最近変更が入った」の 3 条件で費用対効果を測る

**派生元**: 2026-04-alarm-12.md, 2026-04-alarm-15.md, 2026-04-alarm-21.md, 2026-04-alarm-29.md, 2026-04-alarm-29c.md, 2026-05-alarm-2.md（CustomPaint 存在確認だけでは描画漏れを検出できないため visual golden 必須）

## P9: git ブランチ統合は「実際のマージ先・コミット同一性・競合ブランチの状態」を都度確認する

コンフリクット判定・ブランチ状態の確認を近似ツールや過去の仮定に頼ると、integration build で意外な失敗を引き起こす。以下を徹底する：

- **コンフリクット判定**: `git merge-tree` はコンフリクット有無の近似報告にすぎない。実際の判定は `git merge --no-commit --no-ff` のみ信用する。integration build スクリプトで merge-tree を採用すると誤検知が起きる
- **cherry-pick 後のブランチ管理**: cherry-pick でマージしたブランチはコミット ID が変わるため `git branch --no-merged` から消えない。`git rebase origin/main` で先端を main HEAD と一致させて force-push するまで残り続ける
- **並行ブランチのコンフリクット解消**: 同テーマの並行ブランチ（リトライ系・prefix 系等）は main ベースでのコンフリクット解消後も、先行マージ済みブランチがある統合先（staging-integration 等）で再コンフリクットが発生する。解消は必ず「最終マージ先の現在状態」をベースに行う
- **レビュー承認と main 到達は別事象**: レビューが承認された時点で archive すると、未マージのブランチが archive に埋もれて監査から外れる。archive は `git cherry` で main 到達を実測してから行う。レビュアー（人でも AI でも）が承認と同時に archive しようとしたら差し戻す
- **マージ済み判定は cherry で行う**: ブランチが main に取り込まれたかは `git merge-base --is-ancestor` ではなく `git cherry main <branch>` で判定する。clean rebase 後に別 SHA でマージされたブランチは ancestor 判定では「未マージ」に見えるが、cherry なら等価パッチを `-` として検出できる。rebase を多用する自動実装パイプライン（worktree → push → 統合ビルドでのマージ）では旧 tip が dangling で残るのが常態

**派生元**: 2026-07-logsite-3.md, 2026-07-logsite-8.md（コンフリクット連鎖は解消→リビルド→次ブランチ確認のラウンド単位で回す）, 2026-07-logsite-12.md（cherry ベースのマージ判定・rebase 後の旧 tip 誤検知回避）, 2026-08-logsite-2.md（承認と到達の分離）

## P10: repo 正本・外部ストアキャッシュの同期は「書き戻し・乖離検出・列単位の追随」を設計時に揃える

repo を source-of-truth、外部ストア（DB・ポータル・キャッシュ）を派生とする構成では、片方向 sync が silent な乖離を生む。以下を設計時に揃える：

- **書き戻し経路**: 外部ストアで Human 判断・状態変更を受け付けるなら、repo への書き戻し経路をセットで用意する。片方向 sync の Human ゲートは判断が silent に失われる（portal 判断 4 件が D1 に眠ったまま consult が再質問した実例）。判断の正本＝repo ファイル、他ストア＝キャッシュと明示する
- **乖離検出**: 状態ストアを跨ぐ機能（sync・キュー・キャッシュ）には「両側を突き合わせる invariant check（report-only）」を同じ cron に同梱する。fix と detector は別物で、fix だけでは同型欠陥の再発を検出できない
- **列単位の追随を把握**: sync スクリプトが「どの列をいつ更新するか」（forward-sync candidate の絞り込み条件等）を把握する。repo 側を更新しても、sync の対象外になる状態（例: done にした HO の handoff_status 列）は外部表示に追随しない。反映を指示されたら sync ロジックの実装を先に読んでから、直接更新が必要かを判断する

**派生元**: 2026-07-logsite.md（Human 判断ストアの書き戻し + 乖離検出セット / 状態ストア跨ぎの invariant check 同梱）, 2026-07-logsite-12.md（sync の列単位追随を確認してから反映・handoff_status が done HO に追随しない設計の実例）

## P11: AI エージェントがクライアントの API は「往復・容量・制御層・検証手段」で設計する

人間がクライアントの API では許容される設計が、AI エージェント相手では体験を壊す。往復1回＝推論1回＝待ち時間として直接跳ね返るため、以下を設計時に揃える：

- **エラーで学ばせない**: CHECK 制約・enum・値域など「弾かれる入力」は、エラーメッセージではなくスキーマ説明文に明記する。人間なら1回失敗して覚えれば済むが、エージェントでは失敗のたびに往復1回＝待ち時間が発生する
- **1操作1往復に集約する**: 頻出する読み取り・書き込みは複合ツールにまとめる（1ターンの書込みは1回、読み取りも1回）。ツールを追加するときは「往復が増えないか」を先に検討する
- **常時プロンプト層は有限資源**: instructions・システムプロンプト・中核ルールには文字数上限を守るテストを置く。追加は「何を落とすか／どう圧縮するか」の棚卸しとセットで行い、上限テストを緩める方向で解決しない
- **制御層を2つに分ける**: **振る舞いの方針**（いつ何を呼ぶか・出力の組み立て方）はサーバー側のルールに置くと可搬だが効力はベストエフォート。**ランタイム設定**（モデル選択・思考量・ストリーミング）は環境側にしか置けず確実だが非可搬。MCP プロトコルに思考量を制御する機能は無い、のように「どちらにも置けないもの」を先に把握する
- **出力の質は自動テストで検出できない**: 保存された状態が正しくても「人間に見せた文章」が誤っている類の欠陥（情報層の漏洩・冗長な管理情報）は、全テスト green のまま発生する。実使用（ドッグフーディング・テストプレイ）が唯一の検出手段になる領域があると認めて、検証計画に組み込む

**派生元**: 2026-08-trpg.md（record_turn の acquisition_type 語彙未記載で往復増 / instructions 4000字上限に抵触 / 提示文への GM 層漏れが 142 テスト green 下で発生 / 思考量制御は MCP に存在しない）

## P12: 自動化は「滞留時間・生産量・届け先」で監視する

形が正しいまま何も産まない状態は、既存の自己修復機構では検知できない。ジョブが全て成功と記録されながら 24 日間 1 件も成果が出ていなかった実例から、以下を設計時に揃える：

- **握り潰した失敗は別経路で可視化する**: `|| true` / best-effort は本体を止めないために正しいが、記録の欠落と組み合わさると「全ジョブ成功なのに何も動いていない」を作る。握り潰すなら、失敗が別の場所に必ず現れる経路を同時に用意する
- **lock は flock に統一する**: PID ファイル + `trap EXIT` は SIGKILL・再起動で trap が走らず stale 化し、以降の全実行を無言でスキップさせる。プロセス終了で自動解放される仕組みを使う
- **ドリフトではなく滞留時間と生産量を見る**: 既存の自己修復（鮮度修復・stuck reset・再トリアージ・乖離監視）は全て「状態の崩れ」を直すもので、「正しい状態のまま停滞している」は対象外。「最後に成果物が出てからの日数」のように、稼働時間に左右されない指標で測る
- **検知には届け先を持たせる**: 画面を見に行く前提（pull 型）の可視化は、常時起動でない環境では届かない。検知した異常が人間の目に入る経路をセットで実装しないと「作ったが効かない」で終わる
- **リトライ上限は時間ベースの解除とセットにする**: 上限だけを設けると、原因を直しても手動で state を消すまで復旧しない。冷却期間後に自動で再挑戦する経路を必ず持たせる
- **誤警報を放置しない**: exit code は「失敗」と「することが無い」を分ける。鳴り続ける警報は監視そのものへの信頼を失わせる

**派生元**: 2026-08-logsite.md
